# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.



## Build & Run

Cargo workspace with three members (root `Fractals`, `frac_lang`, `frac_lang/frac_lang_lsp`).

- `cargo run` — launches the egui GUI app (`Fractal Generator`). Two modes: **Classic** (2×2 pixel-permutation fractal) and **Frac** (loads `.frac` substitution-tiling files).
- `cargo build --release` — release build.
- `cargo test -p frac_lang` — runs tests in the language crate. Use `cargo test -p frac_lang <pattern>` for a single test.
- `cargo build -p frac_lang_lsp` — builds the LSP server binary used by the VS Code extension.
- `cargo run --bin dump_normalized.rs <path-to-.frac>` — runs test code to show the LSP output for a frac file.
- VS Code extension lives in [editor/frac-vscode/](editor/frac-vscode/); build with `cd editor/frac-vscode && npm install && npm run compile`. It locates the LSP via the `frac.serverPath` setting, `FRAC_LSP_PATH` env var, or `PATH`.

Helper scripts (Python, no deps): [convert_patterns.py](convert_patterns.py) converts the legacy 2×2 JSON pattern format to `.frac`; [trace_spec.py](trace_spec.py) and [trace_perms.py](trace_perms.py) are debugging aids.

## Architecture

The repo contains **two related fractal systems** that share a GUI:

### 1. Classic 2×2 fractal ([src/main.rs](src/main.rs))
A single ~1000-line file implementing a recursive 2×2 pixel-grid substitution. Each `Pixel` has an RGBA `Color` plus a `Permutation` (one of the 6 rigid motions of the unit square). The image is generated by recursively replacing each pixel with a permuted copy of the base 2×2 pattern. Patterns serialize to JSON. The legacy `.json` patterns in [patterns/](patterns/) belong to this system.

### 2. `frac_lang` — substitution-tiling DSL ([frac_lang/](frac_lang/))
A small language for declaring polygonal substitution tilings (Penrose, pinwheel, etc.). Pipeline, all under [frac_lang/src/](frac_lang/src/):

`source.frac` → **lexer** → **parser** → `ast::File` → **normalizer** → `NormalizedFile` → **evaluator** → `RenderTree` → rasterized in `src/main.rs`

The normalizer is the heart of the language. Its submodules in [frac_lang/src/normalizer/](frac_lang/src/normalizer/) run sequentially and are designed to be readable in order: `geom` → `symmetry` → `topology` (builds a planar graph from tile boundary + declared cuts and enumerates faces, each becoming a child tile) → `typecheck` → `acyclicity` → `group_perm` → `canonicalize` (the normalizer rewrites source into a canonical form on save — symmetry groups are inferred, never written).

Four top-level item kinds in a `.frac` file: `tile` (polygon + sides + canonical vertex list), `partition` (cuts that subdivide a tile into typed children), `fn` (pure helpers), `pattern` (root: state, color rules, recursive rules). Child polygons are **derived** from the planar graph — never written directly.

Authoritative specs live alongside the code:
- [frac_language_spec.md](frac_language_spec.md) — full language semantics.
- [frac_lang_doc.md](frac_lang_doc.md) — user-facing writing guide.
- [spec_deviations.md](spec_deviations.md) — known places the implementation diverges from the spec; read before debugging normalizer edge cases.
- [frac_lang_plan.md](frac_lang_plan.md) — implementation plan / status.

### 3. LSP ([frac_lang/frac_lang_lsp/](frac_lang/frac_lang_lsp/))
Thin server: `document` tracks open buffers, `diagnostics` re-runs parser+normalizer on change, `hover` surfaces normalized data, `line_index` maps spans. Errors flow through `ast::ParseError` / `normalizer::NormalizeError`, both of which carry `Span`s used for diagnostic ranges.

## Conventions to know

- The spec and [frac_lang_doc.md](frac_lang_doc.md) describe canonical rewriting "on save", but this is **not yet wired up**: the LSP ([frac_lang/frac_lang_lsp/src/main.rs](frac_lang/frac_lang_lsp/src/main.rs)) only advertises `text_document_sync` + `hover_provider` and has no formatting/save handler. A `printer` module exists ([frac_lang/src/printer.rs](frac_lang/src/printer.rs)) but is not invoked by the editor.
- Boundary-vs-interior vertex distinction in `partition` blocks is load-bearing: any point lying on a parent edge must be declared `edge`, even when geometrically "inside" relative to a child face. See [frac_lang_doc.md](frac_lang_doc.md) for the canonical example with `tri.tri_split`.
- Workspace root is also a package (`Fractals`), so `cargo run` without `-p` runs the GUI.
